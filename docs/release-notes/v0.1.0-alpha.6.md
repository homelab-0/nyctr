Sixth alpha. A collection no longer stops Nyctr from answering, what has left your network stops being counted and is dropped after a week, Nyctr decides for itself which address a request came from, and an administrator can connect the model from the console.

Still a prerelease. Read "Upgrading" before you install it: the list of your proxies has a new name, and with more than one proxy in front of Nyctr there is a setting to add. Nothing in this release was run against a real source by this build; see "Not verified".

## What changed

### Collection no longer stops the server

- **The console and the readiness check keep answering during a collection.** What a collection read is now stored on a separate thread, in a fixed number of database statements instead of one per item and per lookup. On the test stack the longest health answer stayed under 0.55 seconds across 65 collections of a large site and a busy DNS source. With the previous release, on a real network, Nyctr stopped answering for 7 to 11 seconds at each collection.
- **A DNS source is read from where the last read ended**, less ten minutes, so each collection reads only what is new. The whole time window is read the first time, after the source is edited and while no lookup is stored. After a failed collection the next one picks up from the last one that was stored.
- **"Partly collected" now clears by itself.** A DNS source whose read kept only the most recent lookups stays partly collected until the stretch it missed is older than the source's time window, and the source card and the Briefing say so. If it stays partly collected, give the source a shorter time window.
- **Each collection writes a start line and an end line to the server log**: the source, who started it, how long it took, how much was read and how much was new, and the outcome. The server log now shows Nyctr's own information lines, which it used to drop.

### What has left the network

- **An item a source stopped reporting is marked and no longer counted.** It is marked only after a collection that read that kind of item in full. A collection that failed, or could not read a list of items, marks nothing, and one that was cut short marks nothing of the kinds it cut short. A collection that missed only a detail, such as guest passes or Wi-Fi names, still marks. The Briefing, Inventory and the remove dialog count only what is present and say how many items were not seen at the last collection. Inventory keeps a missing item with its mark, the device table in Setup says how long ago it was first missed, and the Map leaves it out.
- **A missing item is dropped after a week.** It goes once whole reads on seven separate days, the last at least seven days after the first, have all left it out. A device that comes back before then is the same device with everything attached to it. Nothing is dropped from a source that was down or is rarely collected until it has been read on seven days. With a dropped item go its access point history, the record of what Nyctr did to it as a guest, its lines on the Map, and a finding that rested on it alone. Requests and their history, exceptions and Activity records are never dropped.
- **What a person attached to is kept.** A device assigned to someone or filed by an administrator, and an item linked to a DNS label, stay marked and uncounted until the assignment, the link or the source is removed. So does anything Nyctr still holds: an address with an open exception or a waiting request, a device a stored lookup is tied to, and a guest Nyctr cut off or whose access has not run out.
- **A blocked address goes when no stored lookup names it.**
- **Expired lookups are removed every half minute**, not only when someone opens Blocks. Each drop is recorded in Activity, one line per source, with how many of each kind went.

### Which address a request came from

- **Nyctr works out the address itself.** A connection that does not come from one of your listed proxies is the client, and whatever it says about another address is ignored. Behind a listed proxy, Nyctr counts from the right of the `X-Forwarded-For` header and takes the entry your own proxy wrote. With more than one proxy, it believes that entry only when every proxy in between is listed too; otherwise it records no address.
- **A new setting counts your proxies**: `NYCTR_PROXY_HOPS`, or `proxyHops` in the chart, 1 by default.
- **The list of proxies has a new name**, `NYCTR_TRUSTED_PROXIES`. The chart value keeps its name, `forwardedAllowIps`. The old name, `FORWARDED_ALLOW_IPS`, is still read for this release when the new one is empty, with a warning in the server log and in Setup.
- **A list that trusts every address stops Nyctr from starting** and says why. That includes `0.0.0.0/0`, `::/0` and ranges that together cover every address.
- **The sign-in limit counts by the same address.** Requests whose address cannot be told share one limit.
- **Setup shows an administrator "The address Nyctr sees for you"**, under This installation: the address, where the connection came from, and which entry was read, or why there is no address.

### The model, from the console

- **Setup has a Model card.** An administrator sets the endpoint, the model's name, the name of the secret that holds the key, how calls are traced and a time limit, and presses Test. Test sends one fixed question and says in plain words whether the model answered, the endpoint refused, it could not be reached, the answer was in another shape, or no answer came in time. The card says whether the value in force was saved in the console or set on the server. A value saved in the console replaces the server's own.
- **The key is named, never typed.** The card takes the name of a server secret, which must start with `NYCTR_MODEL_SECRET_`. The key is never shown.
- **The model can only be on servers the operator lists** in `NYCTR_MODEL_HOSTS`, besides the one in `NYCTR_AI_BASE_URL`. Each entry is a server. A bare name means HTTPS on port 443 only; any other port, or plain HTTP, is written in full, such as `https://llm.example.org:8443` or `http://proxy.example:4000`. An address with a sign-in name, a password, a query, or a cloud metadata or link-local host is refused, and no redirect is followed.
- **Calls can carry trace headers for a tracing proxy** in front of the model. An installation that sets the model only on the server sends none unless `NYCTR_AI_TRACE` is set. **Where no model is set on the server, the card offers trace headers for a tracing proxy by default: saving a connection without changing that choice turns trace headers on.** Where the server has a model, the card opens with the server's choice and saving keeps it. A trace says what a call is for and which version of Nyctr sent it, never a person, a device, an address or the key.
- **A saved connection that cannot be read turns the model off** with a plain message on the card. It does not fall back to the server's own endpoint and key.
- **Activity records each save and each test.** A save is recorded with the model's name and its server, a test with how it went.
- **A model cannot be connected from the console in Demo mode.** Demo keeps answering from samples unless the operator set a model on the server.

## Upgrading

- **Nyctr collects by itself.** As in the previous release, a live installation collects from every saved source on a schedule: every 15 minutes unless you say otherwise, with the first collection about half a minute after it starts, or later if the last scheduled collection was less than one interval before. Change the interval or switch the schedule off in the console: Setup, "This installation". The deployment value `NYCTR_COLLECT_INTERVAL_SECONDS` (the chart's `collection.intervalSeconds`) is only a starting interval until a schedule is saved in the console. Its default, 0, means "not set", so the 15 minute default applies; it does not switch the schedule off, and the chart does not send it. Demo mode never collects.
- **Changes at sources stay off** unless an operator names the integration in `NYCTR_PROVIDER_WRITES`, as before. The assistant stays off until a model is connected.
- **The list of your proxies has a new name.** Move it from `FORWARDED_ALLOW_IPS` to `NYCTR_TRUSTED_PROXIES` and remove the old name. The old name is still read for this release, with a warning, and will stop working in a later one. The chart value `forwardedAllowIps` keeps its name and now fills the new variable, so chart users change nothing. The Compose production file accepts either name and refuses to start with neither.
- **With one proxy** that adds the address it saw to `X-Forwarded-For`, nothing else changes. **With more than one proxy** in front of Nyctr, such as an edge in front of a cluster's gateway, list every one of them and set `NYCTR_PROXY_HOPS` (`proxyHops`) to their number. Until you do, everyone behind the edge is seen at the edge's address, shares one sign-in limit, and no device is recognised for them. If an edge's addresses cannot be listed, leave the count at 1: people behind it then appear at the edge's address, which is wrong for them but cannot be forged. After upgrading, sign in as an administrator and check the address in Setup.
- **A proxy on Nyctr's own host or in its own pod must now be listed.** The previous image believed `127.0.0.1` without being told. This version believes only the proxies on the list, so an unlisted proxy there is taken for the client: everyone is seen at `127.0.0.1`, shares one sign-in limit, and no device is recognised for them. Add `127.0.0.1` to the list if you have such a proxy.
- **A list that trusts every address stops Nyctr from starting.** Fix the list if the new version does not start.
- **The image now starts its web server with that server's own forwarded-header handling off.** If you start Nyctr with your own command instead of the image's, add `--no-proxy-headers`.
- **A DNS source may read as partly collected for up to a day after the upgrade.** The first collection after the upgrade reads the source's whole time window, because the previous release did not record where its reads ended. On a busy source that read keeps only the most recent lookups and leaves a gap before them. Later collections read only what is new, and the source shows as connected again once that gap is older than the source's time window: 24 hours unless you set it longer, up to 72.
- **What a source no longer reports stops being counted at once.** The previous release already marked such items, and still counted them. From the start of this version those marked items are left out of the counts and off the Map. The seven days before anything is dropped start at the first whole collection after the upgrade, so nothing but blocked addresses is dropped in the first week. Blocked addresses are different: within about an hour after a source's first collection by this version, every blocked address that no stored lookup names is deleted, which on an installation that has run for a while can be many at once.
- **No database schema change.** Upgrading from v0.1.0-alpha.5 runs no migration. The model connection and this installation's key for naming trace sessions are new rows in the existing settings table. When an item went missing and on which days are kept in the item's own attributes, and where a DNS read ended is kept in the collection's Activity record. Activity has three new kinds of record: a change of the model connection, a test of the model, and items dropped from a source.
- **Going back to the v0.1.0-alpha.5 image** works on the newer database but loses this release's behaviour. That image ignores a model connected in the console and uses the server's own settings, counts missing items again (what was dropped stays gone), reads every DNS source's whole window again, and shows the three new kinds of Activity record as "Something this version of the page cannot describe". It reads only `FORWARDED_ALLOW_IPS`, so go back to the v0.1.0-alpha.5 chart with it, or set the old name again in Compose. Do not run the two images side by side on one database; the chart replaces the old copy before it starts the new one.
- **New server settings**, all optional: `NYCTR_TRUSTED_PROXIES` (empty: no proxy is believed), `NYCTR_PROXY_HOPS` (1, between 1 and 10), `NYCTR_AI_TRACE` (`off`; also `standard`, `proxy` or `proxy_body`), `NYCTR_MODEL_HOSTS` (empty: no server besides the one in `NYCTR_AI_BASE_URL`), and one `NYCTR_MODEL_SECRET_<NAME>` per key the console may name (none). The chart gains `proxyHops` (1), `assistant.trace` (`off`), `assistant.hosts` and `assistant.secrets` (both empty). `FORWARDED_ALLOW_IPS` is now the old name of the list. No other setting was added or changed.
- **If you call the API yourself:** new routes `GET` and `PUT /api/model`, `POST /api/model/test` and `GET /api/me/address`, each for an administrator on the console address. `GET /api/overview` counts leave out missing items and gain `missing_counts`; `GET /api/graph` leaves missing items out; the removal preview gains `missing`. The read-only graph query still lists missing items, each with a `missing` mark. `PUT /api/model` without `trace` saves `proxy`, the style for a tracing proxy. Routes were only added, none removed.
- The image is `v0.1.0-alpha.6` and the chart is `0.1.0-alpha.6`, the same pairing as before.

## Validated

With fabricated data only, on one Linux x86-64 machine:

- The API, release and acceptance-helper test suites, the lint and format checks, the console tests and the console build, on this release's commit. The chart tests with Helm 3.22.1 and Helm 4.3.1.
- A walk through the merged build in a real browser (headless Chromium) at 1440 by 900 and 390 by 844, before this release:
  - on the Docker acceptance stack, the production image in live mode against a fabricated gateway and DNS service, started read only and again with changes allowed: collections of a large site and a DNS source over its read limit while the health check was asked ten times a second, items that left the network marked and left out of the counts, opening, ending and expiry of access at the source, across a restart too, and a restart during a collection;
  - in Demo mode, every console page and the member's pages, signed in as the administrator and as the member;
  - the Model card against a stand-in endpoint on the same machine, at 1440 by 900 only: each refusal the card's form can reach, a save, Test and the assistant. A request to explain a finding was sent as well; the stand-in answers in plain text, so Nyctr said it could not read the answer. The key reached the stand-in only in its `Authorization` header and only at the allowed server, and no trace header named a person, a device or an address.
- The walk found nothing that blocks the release. The one new thing of weight is the restart during a collection, under "Known issues". It also found smaller problems of wording and layout, most of them already known from the previous release; those a person running Nyctr would trip over are under "Known issues".
- Each change was reviewed independently before it was merged, and its findings were fixed and checked again.
- Earlier, while these changes were built: the store and drop steps against PostgreSQL 17 as well as SQLite, and the number of database statements a collection runs, counted on both.

## Not verified

- **Nothing in this release was run against a real source by this build.** Tests and the walk above use fabricated answers.
- **What the previous release showed on one real network**, read only: the schedule ran against a real gateway and a real DNS service, the gateway was recognised, devices were placed on their networks, and the server stopped answering for several seconds at each collection, which this release fixes.
- **How long the store takes at that network's size.** It was measured on fabricated data of that shape only.
- **A DNS source picking up from where it stopped across days.**
- **Dropping after seven separate days.** It needs a week to happen. On the acceptance stack only marking could be seen, and a blocked address could not be made to leave there; dropping is tested with a set clock.
- **The address rule behind a real cluster's gateway.** The acceptance stack sends no forwarded header, so a listed proxy was tried in tests only.
- **A model reached through a real tracing proxy.** The headers were checked against a stand-in only, and follow the proxy's public documentation.
- An upgrade of an installed v0.1.0-alpha.5, chart or image, was not run anywhere, and neither was an installation of the chart in a cluster. CI installs the chart fresh in a throwaway cluster.
- Everything listed under "Not verified" in earlier releases still applies.

## Known issues

- **A restart during a collection leaves the source showing it is still collecting.** For five minutes Collect is refused with "A collection is already running" and Remove is refused too, though nothing is running. After that the source still shows it is collecting until its next collection; with the schedule off, until someone presses Collect. An update restarts Nyctr, so this will happen.
- **A guest pass cannot be issued from the console when more than one network source is saved.** The form names no source, so Nyctr takes the first by name. By API it can, by naming the source.
- **An opening at a DNS source applies to everyone on that DNS profile** until it ends. The console says so before approval.
- **For five minutes after an opening that could not be confirmed,** an entry for that address added by hand at the source is taken for Nyctr's own and removed. Do not add the address there while Open now lists it as not confirmed. A source that applies an add more than five minutes late leaves an entry that nothing on record removes.
- **Blocked lookups cannot be tied to a device when the DNS source names none,** for example when a gateway forwards every lookup to the DNS service under its own name. A member is then shown nothing to ask for, only that one of theirs may be missing and who to ask.
- **The member portal does not refresh by itself after a request is decided.** The member keeps reading that a person needs to look at it until the page is reloaded.
- **Open now does not refresh by itself.** A "Not confirmed" row that Nyctr has since settled stays on screen until the page is reloaded. If both the add and Nyctr's own removal are answered late, the entry is removed but the record says nothing was removed.
- **After a model is connected, the assistant still says to connect one** until the page is reloaded.
- **Once a model is saved in the console, there is no way back to the server's own setting** except saving the server's values in the card.
- **On SQLite, a request that changes something waits while a collection is being stored,** and fails if that takes more than five seconds. The Compose files and the chart use PostgreSQL, where only a change to the source being stored waits.
- **A guest Nyctr cut off that has since left the network holds back removal of its source,** and is never dropped. Letting it back on can fail at the source once the device is gone.
- **With no proxy listed, the address panel in Setup suggests adding the address it sees to the list of proxies.** Behind no proxy, for example in the Docker quick start where it shows the container network's address, do not: Nyctr would then believe what any client says about its address.
- **Guests still counts and lists a guest its source stopped reporting,** with no mark, where Inventory and the Briefing leave it out.
- **Counting risk bands on Blocks slows down** past about 60,000 stored lookups (about 1.5 seconds at 100,000), because the band is not stored and every lookup is scored to count it.
- **"Opened automatically N times" on a suggestion counts every opening the access rule decided,** including ones that changed nothing at a source because changes are off.
- **While a retry is pending,** the source card shows the time of the next scheduled collection and not the next try. Activity shows the next try.
- **Once a source has collected, where it reads cannot be changed.** Add a new source, then remove the old one. Removing a source deletes the device assignments and label links made on its devices.
- **Only IPv4 ranges are read.** A device with only an IPv6 address is not placed, and one network whose range could not be read leaves that whole site's devices under "Network not reported" until a later collection reads it.
- **Two site shapes can be filed wrongly as a gateway,** both at a site whose router is another vendor's: a core switch with an address outside every range and equipment below it, and an old out-of-range switch that one access point still names as its uplink. Either is labelled as worked out by Nyctr.
- **A connection test through the cloud address** waits at most 20 seconds for its turn. For a site that needs more than 96 requests it cannot finish there, though collections of the same site do. Two copies of Nyctr on one database pace separately.
- **A guest change that a source applies late is not followed up** the way an opening is: a guest let on late shows as on after the next collection, and a pass created late shows as the source's, not Nyctr's.
- **A DNS lookup the source lists more than ten minutes after it happened may be missed** by a read that picks up where the last one ended, and the older lookups a cut-short read left out are not gone back for.
- **The chart's `assistant.hosts` cannot hold an IPv6 address yet.** The server setting itself takes one.
- The limits listed under "Limitations to resolve before a production release" in `docs/security-model.md`.
