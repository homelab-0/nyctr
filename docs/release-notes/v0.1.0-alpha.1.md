First alpha of Nyctr, a self-hosted console for seeing what a network blocked, letting people ask for temporary access, and managing guest Wi-Fi.

This is a prerelease. Nothing in it has been run against a real UniFi console, NextDNS profile, Proxmox cluster or Pi-hole. Every integration was written from the provider's documentation and tested against made-up responses. Expect to find differences on first contact, and please report them.

## What is in it

- **Console and member portal.** Briefing, network map, inventory, findings, blocks, requests, open exceptions, guests, sources, activity and setup for administrators; a plain portal for members to see their own blocks and ask for access.
- **Vendor-neutral core.** Each integration declares what it reads, which capabilities it adds and what it can change. Shipped: UniFi Network and NextDNS, plus Proxmox VE and Pi-hole v6 as experimental.
- **Risk score.** Rule-based, from the reason the source gave and the shape of the name. Unknown stays unknown. It is not a reputation lookup.
- **Access rule and leases.** An administrator-written rule may open a low-risk privacy-list block for a limited time. Everything else waits for a person. Every exception is a lease that is closed again, including after a restart.
- **Guest Wi-Fi.** Guests sign in on the network's own page. Nyctr issues passes, shows who is on, and can cut a device off or lock it out, by hand or by a counted rule.
- **Assistant and queries.** A rule-based attention list, optional questions and finding insights through any OpenAI-compatible endpoint, and a read-only graph query browser.
- **Packaging.** One image for amd64 and arm64, a Compose file and a Helm chart.

## Safe by default

- Collection only reads.
- Nyctr changes a source only when its integration is named in `NYCTR_PROVIDER_WRITES` (Helm: `providerWrites`). Empty means read-only.
- Automatic collection, the collection webhook and the assistant are off until configured.
- Credentials stay in server environment variables. The console only ever sees their names.

## Not verified

- No run against real providers. See above.
- The assistant has only been tested with a stubbed model.
- The upgrade from the earlier database schema is tested on SQLite only. A fresh PostgreSQL database is tested in CI.
- Creating and deleting a guest pass is not read back from the provider at the time; the next collection shows any difference.
- One application process does everything. There is no separate worker.

## Suggested first run

1. Deploy read-only and sign in.
2. Connect one source, run its connection test, then collect. Compare the map and inventory with what you know is there.
3. Repeat for each source.
4. Only then allow changes, one integration at a time: open one low-risk address and watch it close; issue one guest pass and cut one test device off.
