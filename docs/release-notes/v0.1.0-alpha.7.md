Seventh alpha. Members can ask about a site that did not open from signed-in Nyctr, including when the DNS source did not name their device. Requests are analysed before the administrator's access rule decides, and an administrator can receive notices when a person needs to act.

This is an experimental prerelease. Back up the database before upgrading from alpha.6: this release migrates it, and the alpha.6 image cannot start against the newer schema. No production upgrade or real provider opening was validated for this release.

## What changed

### A member can name the site

The signed-in **This device** page has a form for a site that did not open. Nyctr must recognise the current device as one the member may use, through an assignment or a live sign-in tie. Recognition is an administrator-controlled setting that starts off. The page can show the device a member signed in on without an administrator assigning it first, when recognition is enabled and the network source can identify it.

For a new request, the typed name must match an exact blocked DNS name observed in the last 15 minutes and still retained. A parent domain or subdomain does not count as that match. This lets a member ask about a block whose DNS record names no device; it does not give them another member's browsing history. Nyctr records the request as the member's statement about this device, rather than claiming the DNS source identified who made the lookup.

Each member gets five counted attempts in a fixed hour starting with their first counted attempt. A valid name that misses and a repeat both count. A malformed name or a refusal to recognise the device does not. A repeat of an open request for the same member, device and block returns the stored request.

The API checks the sign-in, current device access, exact name, time window and quota. Before an automatic opening it checks again that the account is active and the member still has an assignment or live tie on that device. The request and its history stay if those checks stop an opening. A model cannot authorize an infrastructure change.

### Analysis before the access decision

Nyctr gathers facts about the blocked name and stores the model's assessment before applying the access rule. The member gets a short explanation of the check; the administrator can inspect its facts, reasons and uncertainty. A missing model, timeout, unusable answer or an answer that cannot tell is recorded plainly. Unknown risk stays unknown. A request that lacks the evidence its rule requires waits for a person.

The administrator's written rule decides what may open, for how long, and within which daily limits. Advertising and tracker lists and threat feeds have separate off, record-only and on settings. Threat feeds require an assessment saying the block looks unjustified and the risk low, along with the rule's other conditions. Advertising and tracker lists can require that assessment too. Categories, deliberate deny entries, firewall policies, intrusion prevention and unknown kinds of block never open automatically. A model's assessment cannot change those limits or open a deliberate block.

Automatic opening of a site a member typed has its own **Open a site a member named** switch in Setup. It starts off, including for an existing access rule. Turning it on still requires the intended tier, the access rule, current device access and every other check to pass.

### Notices and current status

Setup has a Notices card with a test button. A durable queue can send a webhook when a request needs a person or when Nyctr cannot remove an opening. It retries temporary failures and resumes after a restart. Configure a named server secret to sign notices; without one they are unsigned, and Setup says so. The request link requires sign-in, and receiving a notice grants no approval. See [Notices](../notices.md) for the payload, allowed hosts, signature and retry rules.

Member requests and Open now refresh as decisions and execution change. An approval, a demonstration, a failed change and an opening that has not been confirmed have distinct messages. A failed status read leaves the result unknown and offers a retry. Late replies from an earlier sign-in do not put that member's request or draft onto another member's page.

A source left collecting by a stopped process is now released during startup or after its heartbeat expires. A restart no longer leaves it showing a collection indefinitely.

## Upgrading and enabling access

Stop the old copy and preserve a database backup, the deployed image digest, chart version and values before starting this release. Do not run old and new images against the same database. Migration runs automatically during startup, before the API serves requests.

The published alpha.6 database is **schema 2**. This release advances it to **schema 9**, in order:

| Schema | Database change |
| --- | --- |
| 3 | Sign-in ties in `device_presence` |
| 4 | Cached facts and Nyctr's own DNS lookup records |
| 5 | Collection holder and heartbeat columns |
| 6 | Stored analyses of blocked names |
| 7 | The durable notice queue |
| 8 | Analysis id and analysis claim columns on access requests |
| 9 | Request basis and device columns, hourly statement quotas, and request uniqueness by member and block for events, or member, device and block for statements |

Existing rows keep their values. New request columns start empty; an empty basis is read as an event request. On SQLite, migration may rebuild the access request table to replace its old uniqueness constraint while copying existing columns. The typed-site switch is an existing settings-table value with a default of off, not a separate schema migration.

There is no database downgrade procedure. Alpha.6 refuses schema 9 at startup. To go back to alpha.6, stop the new copy, restore the pre-upgrade database backup and use the matching old image and deployment configuration. Restoring that backup loses changes made since it was taken. Migration tests cover stored-row preservation and a second startup on SQLite and PostgreSQL; they are not evidence of an upgrade of an installed production database.

Before expecting automatic access:

1. Check the address Nyctr sees in Setup, including trusted proxies and their hop count. Enable device recognition if members should use the current-device form, and verify that it identifies the intended personal device.
2. Connect and test the model in Setup. Keep its endpoint and secret within the server's allowed model settings. An unavailable model supplies no verdict; it does not create a low-risk answer.
3. Enable the administrator's access rule and the intended advertising/tracker or threat-feed tier, with suitable limits. Record-only mode records what would have happened and opens nothing. An older flat rule keeps its advertising/tracker limits; threat feeds and typed-site opening stay off. Its new overall daily cap is the old per-person limit multiplied by active accounts, bounded to 1 through 100. Check that cap when upgrading.
4. Enable **Open a site a member named** if typed requests should be eligible to open automatically. Otherwise they wait for a person.
5. Provider changes remain off unless the operator names the DNS integration in `NYCTR_PROVIDER_WRITES` (`nextdns` for the supported opening adapter). Enabling a rule alone does not enable writes. Observe the first real opening and its expiry removal at the provider before relying on them.

No live setting or provider write is enabled by this release preparation. The image version is `v0.1.0-alpha.7` and the chart version is `0.1.0-alpha.7`. Deploy using the digest added below by the publication workflow; there is no `latest` tag.

## Scope and limitations

- An opening at the supported upstream DNS source applies to the whole DNS profile, including other devices using it, until it ends. The request's device identifies who asked; it does not narrow that provider change to one device.
- A gateway's own content filter is a separate control. This release does not collect or open its filtering blocks. Opening upstream DNS cannot bypass a block enforced at the gateway, firewall or intrusion prevention layer.
- The form lives in signed-in Nyctr. It is not an intercepted block page or an unauthenticated captive portal. Guests still sign in at the network source's own portal.
- A provider change that has not been confirmed may still have taken effect. Follow the status and any removal notice, and check the provider before adding the same exception by hand. The existing late-provider and lease limits in [the security model](../security-model.md#limitations-to-resolve-before-a-production-release) still apply.

## Validation

The application changes included here passed 460 console tests, 1,544 backend/release/acceptance tests and eight CI jobs before release preparation, with independent code review. The final member flow was also driven through an isolated local API, real authentication, SQLite and the production frontend at 1440 by 1000 and 390 by 844, with 53 screenshots. The smaller viewport used phone emulation. These checks used fabricated sources and explicit timing and failed-read injections. Earlier backend changes, including migration and access checks, were also tested against PostgreSQL.

Release preparation checks version agreement, release planning against remote tags, release metadata tests, chart rendering, console formatting and a production console build. Publication runs the full CI workflow again on the exact release commit before publishing the image, provenance attestation and chart. The workflow creates the release and tag only after those artifacts succeed.

No real provider-applied opening or expiry close, live-model assessment in this flow, physical handset, production installation upgrade or downstream deployment was validated. Renovate handles the downstream update separately; this release does not establish that it has been applied.
