Third alpha. Members can have their own address, separate from the console.

Still a prerelease, and still true: nothing in it has been run against a real UniFi console, NextDNS profile, Proxmox cluster or Pi-hole.

## What changed

- **A separate address for members.** Set `NYCTR_PORTAL_URL` (Helm: `portalUrl`) to a second origin, for example `https://blocked.example.org`, and keep the console on `NYCTR_PUBLIC_URL`. Someone with a blocked site goes to the portal address; administrators work on the console address.
  - On the portal address every session has member rights, an administrator's included. They see their own devices' blocks and can ask for access; none of the console answers there. The account is not changed, and the page offers the way to the console.
  - On the console address a member gets no session. Single sign-on carries on at the portal address; local sign-in answers with the portal's address.
  - Sign-in returns to the address it started from. The redirect is always a configured origin, never built from the request.
  - A change must come from the address it arrives on.
- **The sign-in page fits the address.** On the portal it speaks to someone whose site would not open, not to the person running the network.

Nothing changes if you do not set a portal address.

## If you turn it on

- Serve both hostnames to the same application. The chart adds the second hostname to its HTTPRoute or Ingress; an Ingress TLS secret must cover both names.
- Add `<portal>/api/auth/oidc/callback` to your identity provider's allowed redirects.
- Create DNS for the second name.

## What it is not

The application tells the two addresses apart by the Host header. That limits what a session can do on each name and keeps the console off the name members use. It is a network boundary only if you also route the two hostnames separately. See "Two addresses" in the [security model](https://github.com/homelab-0/nyctr/blob/main/docs/security-model.md).

## Known limitation

Trusting a proxy *range* (`forwardedAllowIps` with a range, added in v0.1.0-alpha.2) has a gap. A client whose own address lies inside the trusted range, for example another pod in the same cluster going through the gateway, can make Nyctr believe a forged client address. Clients outside the range cannot. Nyctr grants nothing on the address alone: it only picks which of a signed-in member's own devices to highlight, and counts local sign-in attempts per address. The chart README's statement that a network policy admitting only the proxies makes a range safe does not cover this case. Use exact proxy addresses if it matters to you; a fix is planned.
